1. 背景：なぜ自動運転はPost-Trainingへ向かっているのか

自動運転の学習は、「大量logを模倣する一段階」から、「Imitation Learningで基礎能力を作り、その後に追加feedbackで閉ループ行動を改善する二段階」へ移りつつある。 2026年のpost-training surveyは、後段のfeedbackをdistillation、preference alignment、reinforcement learning、test-time refinementの4系統に整理している。Post-Training in End-to-End Autonomous Driving: A Unified View

Stage 1 · Imitation LearningStage 2 · Post-Training
大量のhuman driving logから、通常運転、地図理解、車両操作、多様な交通分布を学ぶ。強いbase policyとhuman-like priorを作る段階。 base policy自身のcandidateやrolloutを安全・進捗・快適性・交通規則で評価し、closed-loopで弱い場面を重点的に直す段階。

Imitation Learningだけでは残る4つのgap

  • Closed-loop distribution shift：学習中はexpert stateを見るが、配備後はmodel自身の行動が次のstateを作る。小さな誤差が時間とともに累積する。
  • Objective mismatch：ADE/FDEやpoint-wise MSEが近くても、片方は衝突・急制動・road departureを起こし得る。学習lossと運転品質は同じではない。
  • Long-tail scarcity：collision回避、yield、takeover、near-miss、失敗後のrecoveryは通常log中に少なく、模倣targetだけでは十分に反復できない。
  • No counterfactual feedback：logはhumanが選んだ一つの未来しか示さない。「別の行動なら何が起きたか」を直接教えない。

Post-trainingはこのgapに対し、modelが実際に生成した複数trajectoryやclosed-loop rolloutへrewardを与え、安全・progress・comfort・interactionという最終目的を直接学習signalへ戻す。特にtrajectory plannerでは、collision、TTC、drivable area、progress、comfortを計算できるため、RL / reward-weighted fine-tuningとの相性がよい。

文献から得る結論：「ILを捨ててRLを一から学ぶ」のではない。大量logで作った強いIL policyをbehavior priorとして残し、RL post-trainingでclosed-loop objectiveとlong-tail failureを補う。成功例の多くもIL loss、KL、EMA、real-log mixingなどでbase competenceを保持している。

本プロジェクトの位置づけ：Original DPをHDPへ置換するのではなく、既存の最良checkpointをStage 1として固定し、HDPで実車効果が示されたAWR lifecycleをStage 2として適用する。

3. HDPのRLをゼロから理解する

HDPはSFT済みplannerを出発点に、次の5段階を反復する。重要なのはpolicy-gradientではなく、trajectoryを生成・採点・重み付き回帰する安定した学習ループである。HDP paper

Step何をするか直感
1 · Sample同じsceneからK本の8秒軌跡を生成一つの問題に複数の回答を出す
2 · Scorecollision、TTC、on-road、progress、lane、comfortを評価各回答を運転品質で採点する
3 · Normalizerewardを同じsceneのK本の中で標準化sceneの難易度ではなく、同じ問題内の良し悪しを見る
4 · AWR update高reward trajectoryのdiffusion MSEを大きくする良い回答を強く復習する
5 · EMA / replay更新をEMAで平滑化し、一定周期で候補を再生成学習を安定させ、改善したpolicyで問題を掘り直す

zᵢ = (rᵢ − mean(r)) / (sample_std(r) + 10⁻⁶)
wᵢ = exp(βzᵢ)
L = mean(wᵢ × diffusion_MSEᵢ)

K=10の意味：10回のPython逐次推論ではない。B×Kを一つのbatchとして5回のdiffusion solver stepを通す。10本は独立Gaussian noiseから始まるため、同じsceneでも異なる候補を出せる。

5. Rewardは何を改善するのか

checkpoint選定に使うscene scoreは、HDP/NAVSIMのPDM scoreをT4データで計算可能な形へ写像したもの。collision、on-road、kinematicは乗算gateであり、重大な失敗はscore全体を0にする。残りはTTC / progress / lane / comfortの加重平均である。

Rscene = no-collision × on-road × kinematic-feasible × (5×TTC + 5×progress + 2×lane + 2×comfort) / 14

指標解決したい場面良い方向役割

Road border狭い右左折、路肩・縁石へのはみ出し車体がdrivable corridor内hard gate

正常なlane changeはどう扱うか

今回のformal runではlane_gate_enabled=falseなので、lane scoreだけでtotal rewardが0になることはない。通常のlane changeはcollision / road-border / kinematicを満たせば候補として残る。一方、T4のroute-centerline proxyが正常なlane changeへ弱いpenaltyを与える可能性はあるため、lane-change sliceを別に公開し、次cycleではHDP論文のexpert lane-change maskを独立ablationする。

6. AWRが学べる条件：候補の多様性

AWRは既存のK候補を並べ替える方法であり、全候補が同じ失敗をすると直せない。したがって「K本あるか」ではなく、stop / go、速度、横方向、曲率などの意味のあるmodeが含まれるかを確認する。

既知の限界：all-zero groupやoverride sceneでは、K=10の中に正解がないことがある。その場合はβを上げず、stop / slow / retrieved repair候補をKへ追加して同じAWR scoreへ戻す。

8. 最終提案

  1. Faithful baselineを完走：現在のHDP-style AWRを途中変更せず、saved EMAをfull validationする。
  2. 単一checkpointを選ぶ：full mean-score CIで最良のEMAだけをreplacement候補にする。
  3. coverageを閉じる：passした場合はcache欠損76,596 sceneをbackfillし、短いconfirm cycleを行う。
  4. 候補がないsceneだけ修復：all-zero / override sceneへR2LPLのmistake miningとrepair candidateを限定吸収する。別SFT branchは作らず、同じAWR objectiveへ戻す。
  5. 主張を段階的に広げる：open-loop full score → reactive simulation → closed-loop → 実車smokeの順で確認する。
