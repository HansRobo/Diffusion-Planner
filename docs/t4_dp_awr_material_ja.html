0. Executive summary

狙いは、既存のOriginal DPを一つのcheckpointのまま、T4全量データでpost-trainし、場面平均の総合運転scoreを上げること。 方法の中核はHDPで実証されたtrajectory-level AWRであり、R2LPLはAWRが正解候補を生成できないoverride sceneだけを補修する。HDPR2LPL

採用

HDPの学習ライフサイクル

同一sceneでK本を生成し、rewardで順位付けし、良い軌跡のdiffusion lossを重くする。EMA、disk replay、周期refreshも引き継ぐ。

T4適用

モデルはOriginal DPのまま

Original DPのdecoder/DiTだけを更新し、lossはplain MSE。HDP固有のvelocity/waypoint headが存在するとは仮定しない。

現時点の結論

最終評価まで判断を保留

正式全量runは既存replay cacheを再利用して継続中。受理可否は全epoch後のsource-relative held-out評価だけで決める。

この資料の可視化は、証拠の強さを混ぜない

A · FORMAL REPLAY

実際に学習へ入ったK=10

epoch-1 cacheからtrajectory・reward・AWR weightを直接読む。衝突/road-borderのscene内contrastを示す最も強い局所証拠。

B · COVERAGE AUDIT

source policyのK=16診断

同僚の可視化器でraw/augmentationの候補coverageを検査。学習後性能ではなく、AWRが「選べる候補」を持つかを見る。

C · METRIC PROBE

構造化counterfactual

意図的にstop/go/shortcut等を作り、evaluatorが区別できるかを検査。model sampleとは呼ばない。

1. AWRを知らない人のための5つの言葉

Scene

一つの運転問題

ego履歴、地図、route、信号、周辺車両とその記録未来を含む。

Policy

軌跡を出すモデル

本資料では既存のOriginal DP。入力から8秒・80点の軌跡を生成する。

Candidate

同じ問題への複数回答

同じsceneからK本の未来を一括生成する。K=10は10回のPython逐次推論ではない。

Reward

回答の採点

collision、TTC/THW、border、red-light、route、progress、comfortなどを評価する。

AWR

高得点回答を強く復習

同一scene内で相対的に良いcandidateのdiffusion lossへ大きい重みを与える。

重要な限界

全候補が悪ければ選べない

K本すべてが衝突なら、βを上げても安全な停止・譲りは生まれない。repair targetが必要。

AWRの最小数式

zᵢ = (rᵢ − mean(r)) / (sample_std(r) + ε)　　ε = 10⁻⁶
wᵢ = exp(β · zᵢ)　　LHDP-faithful = (1/K) · Σᵢ wᵢ · MSE(predictionᵢ, candidateᵢ)
MSEは何と何の誤差か：replayから一つのcandidate軌跡を取り、各updateで独立にdiffusion時刻 t∼U(0.001,0.999) とGaussian noiseを引いてnoisy trajectoryを作る。decoderはscene条件とそのnoisy trajectoryからclean candidateを復元し、正規化後の80点×4 channel（x, y, cos yaw, sin yaw）について二乗誤差を平均する。そのcandidate単位MSEへreward由来のwᵢを掛け、K本を平均する。したがってloss低下は「保存candidateをreward比率で復元しやすくなった」ことを示すが、未見sceneの運転性能向上そのものではない。

正式runは1 replay actionにつき1つの独立t/noiseを使い、prefix teacher forcingなし。encoder、turn-indicator、neighbor loss、HDP hybrid補助、BC anchorは固定/無効で、Original DPのDiTだけを更新する。同じfrozen candidateを別epochで引くたびnoiseが変わるため、replay反復はdenoising objectiveのMonte Carlo再サンプルにもなる。

正式runはβ=1、sample std、normalize_weights=false、awr_loss_reduction=hdp_mean。したがって重み和では割らない。これは公開HDP codeの mean(exp(group-normalized reward) × MSE) と同じ縮約であり、重み和で割る方式は今後の安定化ablationとして区別する。

比較は同じsceneのK本の中だけで行う。critic、PPO clipping、denoising transitionごとのpolicy ratioは使わない。

2. HDP原論文のRLは何をしているか

HDPは、SFT済みのdiffusion plannerを出発点に、複数の完全軌跡を生成・評価・重み付き回帰する。要点は「RLらしい名前」ではなく、良い完全軌跡を学習分布へ戻す安定したライフサイクルにある。HDP paperreleased RL code

1

SFT policy

既に基本運転ができるmodelを開始点にする。

2

K trajectories

同一sceneから複数の8秒軌跡をsampleする。

3

PDM reward

pseudo-closed-loop環境で安全・行動品質を採点する。

4

AWR update

scene内で正規化し、高reward軌跡を重く回帰する。

5

EMA / replay

更新を安定化し、一定間隔で候補を再生成する。

HDP原論文のloss

velocity diffusion lossと積分後waypoint lossのhybrid。HDP固有modelでは幾何連続性の安定化に有効。

pseudo-closed-loopの意味

ego候補は変わるが、neighborは主にログをreplayする。neighborがegoに反応する完全なreactive worldではない。

論文から採用するもの

group normalization、reward-weighted diffusion regression、EMA、disk replay、周期refresh。

EMAの再現境界：HDP論文のparameter tableはEMAを0.05と記載するが、係数の向き・更新cadenceは同表だけでは確定できない。一方、公開NAVSIM packageはuse_ema: falseがdefaultで、ModelEma(decay=0.999)の生成部もcomment-outされている（update/save hookだけが残る）。したがって、今回のdecay=0.999 / optimizer stepは公開releaseのbit-exact再現ではなく、保存ema_state_dictを実車候補として評価するためのT4側で明示した安定化契約である。2,962 stepの1 replay epoch後に開始時EMAが残る係数は0.999^2962 = 0.0516だが、論文の0.05と数値が近いだけで同一定義とはみなさない。

4. 完全なpost-training pipeline

一つのlossではなく、入力契約・候補生成・採点・replay・評価・promotionまでを含む再現可能な運用単位として定義する。

01

Data contract

filtered NPZ、scene hash、train/valid分離、neighbor +1 alignmentを固定する。

02

Scene batch

B scenesを同じego-frameへ変換し、map・route・signal・neighbor maskを検査する。

03

B×K candidate sampling

1回のbatched decoder samplingでK本を生成。各candidateは独立Gaussian noiseを持つ。

04

OBB-aware evaluator

collision、clearance、RB、kinematic、red-lightを先に、route/follow/progress/comfortを後に計算。

05

Group weight

scene内でrewardを正規化し、AWR weight、ESS、top-one share、valid groupを記録。

06

Disk replay

epoch 1は全量candidate cacheを構築。後続epochはfrozen groupをwith-replacementで再利用。

07

DP update + EMA

reward-weighted plain MSEでdecoderを更新し、有効update後だけEMAを進める。

08

EMA paired evaluation / promotion

保存済みEMAをK=1・zero-noise・10 solver stepsでsourceと比較。2,048場面screen後、最大3候補を46,068場面で評価する。

現在の正式run：epoch 1で生成済みのfrozen candidate groupsを再利用し、epoch 2以降をwith-replacement replayで継続する。学習中のK=10/5-step current-policy評価は傾向診断に限定し、checkpoint選定は実際に配備するEMAのK=1/10-step評価だけで行う。
epoch数の再現境界：公開HDP configはreplay_buffer_update_epoch=10かつtrainer上限total_epochs=10000だが、論文は「10000 epochが必要条件」とは示していない。今回のepoch 1 mining + epoch 2–10 replayは、公開実装の最初の1 refresh cycleを再現するもので、10000 epochのbit-exact horizon再現ではない。保存EMAのfull paired結果が合格する場合だけ、最新policyで次cacheをre-mineしてcycleを継続する。不合格のreward/lossを999 cycle反復しても改善証拠にはならない。
noiseを混同しない：mining cacheのK=10は、公開HDP samplingに合わせて10本すべてを独立N(0,I) × 0.5から生成し、さらにtrajectory augmentation std 0.5 mを適用する。zero-noise anchorは含まない。一方、学習monitorは比較を再現可能にするためcandidate 0だけをzero-noiseにし、残り9本をnoise 0.5、augmentationなしで評価する。したがってRdetはmonitor専用の決定論的policy値であり、formal replay図のcandidate 0を意味しない。
OBB座標契約：Original DPのego trajectory点は車体中心ではなく後軸基準。rewardと図ではbox中心を進行方向へ 0.5 × wheelbase 移す。neighborはbox中心基準。ここを同じ扱いにすると、数値上はcollisionでも図では離れて見える誤可視化になる。

5. 指標は「何を解決するか」で読む

Rformal = CollisionGate × DAC(RoadBorder) × KinematicGate
　× (5·TTC + 5·Expert-route Progress + 2·Lane Robustness + 2·Comfort) / 14

これは今回の reward_profile=hdp_pdm のT4実装契約。公開HDP/NAVSIM agentが実際に呼ぶPDMScorerの重み（TTC 5 / EP 5 / LK 2 / HC 2）を基準にしたが、bit-exactなNAVSIM scoreではない。T4 NPZにはNAVSIMのmetric cache、route object、intersection layer、human-history comfort objectがないため、DAC・EP・LK・HCは下表のproxyへ写像し、実行不能軌跡を除くkinematic gateを追加した。red-light、明示的THW/car-following、R2LPL expert-likenessはこのformal totalへ入れていない。

Checkpoint選定の「平均標準」：一つのscene scoreを全sceneで平均する

Dataset Score(π) = 100 × (1/N) · Σs=1..N Rformal(π, s)
ΔScore = 100 × means[Rformal(πAWR,s) − Rformal(πsource,s)]
checkpoint rank = paired-bootstrap 95% CI の下限が最大のepoch
ここが採用判定の主軸：同じ46,068 sceneでsourceと保存EMAを成対比較し、ΔScoreの95% CI下限が0より大きければ「この評価分布の平均scoreが上がった」と判定する。ADE/FDE、collision、road-border、kinematic、lane-change、停止場面は、改善理由と残存リスクを説明する診断内訳であり、単独のpromotion vetoにはしない。これは「安全を無視する」のではない。collision / DAC / kinematicはすでにscene scoreの乗算gateとして強く効き、さらにevent遷移を別表で公開する。

CANDIDATE POOL A · Faithful HDP

Safe-first scoring contract

hard violation = {collision, red crossing, border critical, kinematic invalid}
safe rank = lexicographic(no_collision, no_red, border_margin, TTC/THW, survival)
utility = progress + route/lane + follow + comfort
training reward = safe_rank first, clipped utility second

progressやcomfortがcollision/red-lightを補償してはならない。一方、hard groupが全て同じ0になると学習不能なので、time-to-failureやsurvival marginで安全側のdense creditを残す。

11. 何を満たせば旧モデルを置き換えられるか

1

Exact paired full valid

同じ46,068 scene、同じseed、同じevaluatorでsourceと保存EMAを100%比較。

2

Mean-score improvement

100×mean(Rema−Rsource)のpaired-bootstrap 95% CI下限が0より大きいことをpromotion条件にする。

3

CI-aware checkpoint ranking

平均gainだけでなくCI下限が最大のepochを選ぶ。小標本の偶然のpeakを避ける。

4

Transparent diagnostics

collision / RB / kinematic、ADE/FDE、lane/stop slice、ESSを内訳公開するが、全項同時改善は要求しない。

5

Deployment evidence ladder

open-loop full scoreでcheckpointを選び、reactive simulation / closed-loop /実車smokeで主張範囲を順に広げる。

会議での最終メッセージ

方法は実行可能。中間scoreは有意に改善。

HDPのAWR lifecycleをOriginal DPへ適用する技術経路、full-scale data contract、場面可視化、論文対齐の平均score selectorは整った。2,048-scene monitorでは全epochの平均score gainが正で、epoch 6の暫定Δは+1.530 point。
