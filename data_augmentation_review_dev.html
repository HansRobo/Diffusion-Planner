1. 結論サマリ

A. 「低速データに不適切な augmentation が掛かっている」という仮説は直接的には否定される

quintic 版・bridge 版のいずれも aug_flag に |vx| ≥ 2.0 m/s（7.2 km/h）のゲートがあり、 低速・停車サンプルは摂動対象から完全に除外されている (data_augmentation.py:223-225, data_augmentation_bridge.py:1339)。 したがって「停車中のサンプルの GT が摂動で壊されている」という筋ではない。

停車サンプルに実際に適用されるのは centric_transform（このとき変換行列は恒等）と GT future の unicycle 再構成（平滑化）だけである。後者は本調査で数値検証し、 停車・停車→発進・減速停止のいずれも誤差 ≤ 3 cm、発進タイミングのずれ 0.00 s で、 GT を壊していないことを確認した（§5）。→ この経路はシロ

B. ただし augmentation 側に低速挙動を劣化させうる間接的な経路が 4 つある

  1. 低速域に augmentation が一切かからない（設計上の穴）。停車〜発進域では状態多様性・復帰データがゼロで、 GT 分布をそのまま模倣するしかない。GT 側に「停車継続」が多く含まれていれば、そのバイアスを緩和する仕組みが無い。
  2. 速度・加速度ノイズが運動学的に整合していない （vx ±1.0 m/s, vy ±0.5 m/s, ax ±0.2, ay ±0.1, さらに ego_past と v,a に ±10〜20% のスケール）。 しかも vx,vy,ax,ay はモデル入力ではないため、これらのノイズは入力ではなく 教師（GT 軌跡）を汚染する形で効く。詳細は §6。
  3. quintic の境界条件が現在状態と整合していない。摂動ゼロでも GT が最大 0.18〜0.49 m 書き換わる（§5.2）。 発進直後の 2〜4 m/s 帯では相対誤差が大きい（0.5 s で進行距離の +12%）。
  4. ego_agent_past の座標変換が quintic 版でコメントアウトされている (data_augmentation.py:397-403)。摂動後の自車位置・方位に対して past だけが旧フレームに残り、 地図と past の幾何整合が崩れる。bridge 版では正しく変換されている（:1403-1410）。

C. 低速問題の主犯候補として、augmentation の外に優先確認すべき 2 点

  1. goal_pose の無効値マスクが死んでいる（goal_pose が 3 列で保存されたコーパスの場合）。 heading_to_cos_sin により (0,0,0) が (0,0,1,0) になるため、 centric_transform のゼロ判定マスクが常に False。 「goal 無し」が「自車の現在位置が goal」として入力される。これは停止を強く教える信号になり得る。 マスク自体は a72126ab（branch 到達 2026-07-28）で追加された新しいコードだが、 それ以前もマスクが無かったため挙動は同じ＝ regression ではなく積み残し。→ §7-F, §8.1
  2. IL 学習は skip_for_training フレームをフィルタしない。 train.py は scene_skip.filter_scene_list を呼んでいない (RLVR/PO 側の intake は呼んでいる)。変換器が --write_skipped_npz=1 で 「赤信号停車」「future 進行なし」フレームを出力し、それが学習リストに入っていると、 「停車していて 8 秒間動かない」教師データを直接学習する。→ §10-1

2. 全体データフロー：augmentation はどこで何をしているか

学習 1 iteration の流れ（train_epoch.py:48-70）。赤は問題を含むステップ。

1npz をロード（DiffusionPlannerData）。データは既に ego 中心（ego_current_state[:, :4] = (0, 0, 1, 0)）
↓
2heading_to_cos_sin(ego_agent_past), heading_to_cos_sin(goal_pose) ... (x,y,heading) → (x,y,cos,sin)
↓
3aug(inputs, ego_future, neighbors_future) ← StatePerturbation.__call__。use_data_augment=True のときのみ実行
↓
4heading_to_cos_sin(ego_future) → observation_normalizer(inputs) → compute_training_loss

重要: augmentation は「摂動」だけでなく、正規化と GT 書き換えも兼ねている

StatePerturbation.__call__ は摂動をかけないサンプルにも centric_transform を必ず通す。そこには

  • ego 中心への座標変換（未摂動サンプルでは恒等変換）
  • smoothing_future_trajectory による GT future の全面書き換え（バッチ全体、aug_flag 無関係、既定 ON）
  • 各テンソルの無効要素ゼロ埋め（マスク）

が含まれる。結果として:

  • use_data_augment=False にすると centric_transform ごと消える。 ego 中心正規化を skip しても壊れないのは「データが既に ego 中心だから」という暗黙の前提に依存している。
  • validation は aug を通さない（validate_model.py:61-66）。 すなわち 学習の教師 = 平滑化された GT、検証の教師 = 生 GT という非対称がある （実測差は cm オーダーなので実害は小さいが、設計上は train/valid ミスマッチ）。

ステップ 1: 適用判定 (:223-225)

index 4 = vx（ego 前後方向速度）。|vx| < 2.0 m/s は無条件で除外。

範囲0±0.75 m±0.2 rad

  • vy ±0.5 m/s は車両として非現実的（2 m/s 走行時に横滑り角 14°）。目標 future には一切反映されないので純粋な入力ノイズ。
  • vx は max(vx+Δ, 0) でクリップ (:235)、yaw_rate は ±0.85 でクリップ (:236)。

mask = |v| < 0.2 → steering = 0, yaw_rate = 0
else  steering = clamp(atan(yaw_rate * wheel_base / |v|), ±2π/3)

±2π/3 rad = ±120° のクランプは実車の舵角上限（〜±35〜40°）よりはるかに広く、実質無効。

ステップ 4: 衝突による棄却 (:264-266, 270-344)

_check_aug_validity は SAT による矩形干渉判定で以下を棄却:

  1. 摂動後 ego 矩形 × 全 neighbor の最新フレーム矩形の重なり
  2. 摂動後 ego 矩形 × lanes の left/right 境界セグメントの交差

制約: (a) neighbor は現在フレームのみで、future の干渉は見ていない。 (b) チェック対象は現在姿勢だけで、ブリッジされた future 軌跡が境界を越えても棄却されない。 (c) polygons / line_strings / static_objects は判定に使われていない。

3.2 interpolation_future_trajectory() — 5 次補間ブリッジ (:517-610)

摂動後の現在状態から GT の t = P·dt = 2.0 s 点へ 5 次エルミート補間で接続し、それ以降は GT をそのまま連結。

境界条件の作り方に 3 つの不整合がある (:538-561)

theta0 = atan2(ego_future[:, P/2, 1] - y0,
               ego_future[:, P/2, 0] - x0)      # ← ① 摂動後 heading を使っていない
v0     = torch.norm(aug_current_state[:, 4:6])   # ← ② 符号消失（後退不可）
a0     = torch.norm(aug_current_state[:, 6:8])   # ← ③ 符号消失（常に「加速中」）
...
aT     = norm(fut[P] - 2*fut[P-1] + fut[P-2]) / dt**2   # ← ③ 同様に常に非負
  • ① 初期進行方向を「1.0 s 先の点への弦の向き」で決めており、 せっかく摂動した heading（±0.2 rad）と無関係。加えて曲線では弦の向きが接線から 「1 s 間の方位変化の約半分」ずれる（8 m/s・κ=0.03 で約 6.9°）。
  • ②③ norm によって縦加速度の符号が失われ、減速中のサンプルにも正の加速度が境界条件として与えられる。 始点・終点の両方で起きる。

結果、摂動量が 0 でもこの補間は恒等写像にならない（§5.2 で定量化）。

3.3 __call__() — ego past のスケーリング (:198-213)

W = ego_past_noise_std                      # 既定 0.1
scale = clamp(N(1.0, W), 1-2W, 1+2W)        # → [0.8, 1.2]
ego_past[..., :2] *= scale                  # 過去位置を原点(=現在位置)中心にスケール
ego_current_state[4:6] *= scale             # vx, vy
ego_current_state[6:8] *= scale             # ax, ay
  • 過去の走行距離と現在速度を同率でスケールする「過去速度ノイズ」。future(教師) は変更されないので、 「現在 10% 速い」のに「目標は元のまま」という入力／教師の不整合が意図的に作られる。E[scale]=1 で系統偏りは無いが、 速度入力への感度を減衰させる方向に働く。
  • 位置の乗算スケールなので、曲がった past は曲率も変わる（半径がスケールされる）。

変換行列は R(-θ)、平行移動は現在位置。数式は正しい（vector_transform/heading_transform を検算済み）。 未摂動行では恒等変換になる。

ego_agent_past の変換だけコメントアウトされている (:397-403)

地図（lanes / route_lanes / polygons / line_strings）・neighbors・future は摂動後フレームに変換されるのに、 ego past だけ旧フレームに留まる。摂動行では past の末端が「摂動後の自車姿勢にぴったり到達した直線的な履歴」に見え、 横オフセット・方位誤差が履歴に一切現れない。地図に対する past の向きは Δheading（最大 ±0.2 rad）、 位置は Δy（最大 ±0.75 m）ずれる。bridge 版 (:1403-1410) では有効化されており、2 実装で挙動が違う。

GT future の平滑化 (:415-418)

    ego_future4d = smoothing_future_trajectory(ego_past4d, inputs["ego_current_state"], ego_future4d)

  1. theta_smooth: future 方位を 3 階差分正則化つき最小二乗で平滑化（t0 で 0 に固定）
  2. dxy_theta_to_v: 台形積分の関係から速度列を最小二乗推定。v(0) は ego_current_state[:, 4] に固定

3.5 ゼロマスクは何のためにあるのか

centric_transform の各ブロックには例外なく同じ形のマスクが付いている:

mask = torch.sum(torch.ne(X, 0), dim=-1) == 0   # ← 変換の【前】に「全ゼロか」を記録
X[..., :2] = vector_transform(X[..., :2], transform_matrix, center_xy)
...
X[mask] = 0.0                                    # ← 変換の【後】にゼロへ戻す

意図: ゼロパディングをアフィン変換に対して不変に保つガード

3 つの事実が噛み合っている。

  1. これらのテンソルは固定長ゼロパディングである。 lanes = 区間数 × 点数、neighbor_agents_past = MAX_NUM_NEIGHBORS × T、 static_objects = NUM_STATIC_OBJECTS、… と枠が固定で、未使用スロットは全ゼロ。
  2. パイプライン全体が「全ゼロ ⇒ 無効 / padding」を validity の規約にしている。 各 encoder は attention の key_padding_mask をこの判定から作り、 ObservationNormalizer も全ゼロ要素を正規化対象から外し (normalizer.py:59)、neighbor future の loss 有効マスクも同じ判定 (train_epoch.py:62)。
    encodervalidity 判定centric_transform 側一致
    LaneEncoder (:577)x[..., :8]lanes/route_lanes[..., :8]✔
    StaticEncoder (:501)x[..., :10]static_objects[..., :10]✔
    LineEncoder (:665)x[..., :4]polygons/line_strings 全次元✔（実質）
    NeighborEncoder (:449)x[..., :8]（+ width, length）neighbor_agents_past[..., :6]不一致
    GoalPoseEncoder (:743)mask = zeros（常に有効）goal_pose 全次元概念的に不一致
  3. ところが vector_transform(x, R, bias=c) は R·(x − c)、つまり線形ではなくアフィン。 よって c ≠ 0 のとき padding の (0,0) は R·(−c) ≠ 0 へ移る。 実測（Δy=0.75 m, Δθ=0.2 rad）: padding は (−0.149, −0.735) へ移動し非ゼロ化する。

だから「変換前にゼロだったスロットを記録し、変換後にゼロへ戻す」。 マスクを変換の前に計算する順序が本質である。

マスクを外すと何が起きるか（実測）

有効 2 区間 / 4 枠の lanes、有効 2 台 / 4 枠の neighbors、有効 1 個 / 5 枠の static objects を持つ場面で、 encoder の validity 判定が「有効」と数えるトークン数:

lane 区間neighborstaticnbr future 点
変換前（真の有効数）221160
マスクあり（現状）221160
マスクなし445320
  • padding された lane 区間は、20 点すべてが (−0.149, −0.735) の同一点に潰れた「長さ 0 の車線」になる。
  • padding された neighbor は自車の真横 0.75 m に「大きさ 0・向き未定義 (cos=sin=0) の幽霊車」として出現する。 衝突 loss や road-border loss にそのまま入る。
  • neighbor future の padding 点も非ゼロ化するため、loss の有効マスクが「幽霊を追跡せよ」という教師に化ける。

重要: このマスクが実際に働くのは摂動行だけ

非摂動行は center_xy = (0,0)・R = I なので padding はゼロのまま。 つまりこのマスクは「摂動によって平行移動が入る」ことへの対処であり、 だからこそ centric_transform の内部に置かれている。 augmentation を切れば（use_data_augment=False）不要になる、という構造。

goal_pose の場合は上記の意図が当てはまらない (:432-439)

mask = torch.sum(torch.ne(inputs["goal_pose"], 0), dim=-1) == 0
... 変換 ...
inputs["goal_pose"][mask] = 0.0
  • goal_pose は固定長リストではなく常に 1 個だけ存在する単一エントリ (encoder.py:52: goal_pose_num = 1)。padding という概念が無い。
  • GoalPoseEncoder は mask = torch.zeros((B,1), dtype=bool) で goal トークンを常に有効扱いする (encoder.py:743)。 つまり「無効な goal」を表現する経路が encoder 側に存在しない。
  • したがってあの 1 行は、直後に続く neighbor / lanes ブロックのパターンをそのまま複製したものと読むのが自然 （a72126ab の diff は、既存ブロックと同一書式の 10 行を neighbor ブロックの直前に挿入している）。
  • 発火条件も goal_pose では意味を持たない:
    • 3 列コーパス: heading_to_cos_sin で cos=1 になるため絶対に発火しない（完全に不活性）。
    • 4 列コーパス: (0,0,0,0) で発火するが、これは「自車位置に goal がある」ではなく 「goal 無しの sentinel」。ただし encoder がトークンを消さないので、 ゼロ化は「全ゼロという特定の埋め込み」を作るだけで、無効化ではない。

6.0 前提: 状態量の規約と、そもそも誰が使うのか

  • decoder は ego_current_state[:, :4]（姿勢＝拡散軌跡の t=0 アンカー）と [:, 4:5] のみを使い、後者は縦方向 loss の重みとしてしか使われない (decoder.py:58-61, 119-123)。

（付随して見つかった点: encoder の ego 分岐は ego[:, :6] ＝最も古い 6 フレームを残し、 現在姿勢を含む新しい 15 フレームをゼロ化している。ego_agent_past は 「index 0 が最古 / index −1 が現在」（state_update.py:106-115, bridge:792, unicycle_accel_curvature.py:1114-1116 の 3 箇所で確認）。 一方 neighbor 分岐は [:, :, -6:]＝最新 6 フレームで、規約が逆。 コメントは "Only keep the current + first 5 steps" と書かれており、意図と実装が食い違っている疑いが強い。 augmentation の範囲外だが、自車速度の唯一の手がかりが t = −2.0〜−1.5 s の窓だけになるため、 発進判断への影響は大きい。別途確認を推奨。）

6.1 問題 1 a0 = ‖(ax, ay)‖ は向心加速度を二重計上している

quintic の境界条件 (data_augmentation.py:564-586) は

ẍ(0) = a0·cos θ0 − v0·ω0·sin θ0
ÿ(0) = a0·sin θ0 + v0·ω0·cos θ0

これは「a0 = 接線加速度」を前提とした展開で、向心成分は第 2 項が既に表現している。 ところが実装は a0 = torch.norm(aug_current_state[:, 6:8])、すなわち ‖(ax, ay)‖。 ay ≈ v·ω は向心加速度なので、向心加速度が a0 の中と第 2 項の 2 か所に入る。 さらにノルムなので符号も失われる。終端側の aT（位置の 2 階差分のノルム）も同型。

摂動量を完全にゼロにして、状態と GT を厳密に整合させた合成軌跡で、 ブリッジ区間（0〜2 s）の最大位置誤差を測った。本来は恒等写像なのですべて 0 になるべき。

6.5 整合していた点

  • scale による past 位置 / v / a のスケーリングは相似変換として自己整合している。 位置を s 倍すると弧長も s 倍 → 固定時間格子では v ∝ s, ax ∝ s。 曲率は 1/s 倍になるので ω = v·κ は不変 → ω をスケールしないのが正しい（実装もそうなっている）。 横加速度 v²κ ∝ s なので ay ∝ s → これも正しい。 さらに相似変換は各点の接線方向を変えないので、past の (cos, sin) を触らないのも正しい。
  • steering の再計算 δ = atan(L·ω/|v|) は自転車モデルとして正しく、 vx を下げれば舵角が増える方向に整合する。実機 utils.py:147 と同一式。
  • vx のゼロクリップ max(vx+Δ, 0) は後退状態を作らない安全側の処理。 ただし quintic 側が v0 = ‖(vx,vy)‖ を取るため、後退そのものは元々表現不能。
  • 低速時の ω, δ ゼロ化しきい値 0.2 m/s は実機 utils.py:142 と一致している。

6.6 まとめ — 速度ノイズは運動学的に「適切」とは言えない

  1. ノイズの入れ先が間違っている。 vx,vy,ax,ay はモデル入力ではないので、 入力の頑健化にならず、代わりに quintic と平滑化を通じて教師軌跡を歪めるだけになっている。
  2. 接線／向心加速度の分解ができていない。 norm により符号消失に加えて 向心加速度を二重計上し、定速旋回で最大 1.10 m の目標誤差を生む（§6.1）。
  3. 成分間の運動学的関係が保たれていない。 ay = vx·ω が vx 摂動で最大 ±0.48 m/s² 破れる（§6.2）。
  4. heading 摂動が非現実的な横滑りを生む。 β が Δθ と同じだけ発生し、 さらに ±0.5 m/s の vy が上乗せされる（§6.3）。
  5. 適用順のバグで状態速度と目標初速が最大 ±20% 食い違う（§6.4）。

逆に、scale の相似変換としての整合性と steering の再計算は正しい（§6.5）。

8. 低速・停車〜発進問題への影響評価

「発進していいときに発進しない」に対する各経路の判定。

仮説判定根拠
停車サンプルの GT が状態摂動で壊されている 否定 |vx| < 2.0 ゲートで摂動対象外（§3.1）。摂動・past スケーリングともに aug_flag 配下
停車サンプルの GT future が平滑化で潰されている 否定 停車・停車→発進・減速停止で誤差 ≤ 3 cm、発進遅れ 0.00 s（§5.1）
低速域に augmentation が無いこと自体が原因 有力 該当域は生 GT の完全模倣。GT に「停車継続」が多ければ緩和機構が無い（#D）。§10-1 と併せて確認
速度ノイズが速度と計画の対応を壊している 寄与しうる 速度は入力ではなく教師を汚染する（#E, §6.0）。状態速度と目標初速が最大 ±20% 食い違う（#A4）
モデルが現在速度をほとんど観測できていない 有力・要確認 encoder が ego past の最古 6 フレームのみ残す疑い（#E2）。「今止まっているが発進していい」の判断材料が欠ける
発進直後（2〜4 m/s）の教師が歪んでいる 寄与しうる 加速度符号消失で 0.5 s あたり +12% の前方オーバーシュート（#A, §5.2）。ただし方向は「出過ぎ」側で、症状と逆
goal_pose が「自車位置」として入力されている 有力・要確認 マスク不成立をコードで確認済み（#F）。実データに goal_pose=(0,0,0) が存在するかは未検証
skip_for_training フレームが学習に混入 有力・要確認 train.py はフィルタしない。赤信号停車・future 進行なしフレームが混入していれば「停車継続」を直接学習（§10-1）

読み方

augmentation が停車データを直接壊しているわけではない。問題は「低速域が augmentation の対象外である」という設計の穴と、 速度・加速度ノイズが教師を汚染していることであり、加えて augmentation 外の 2 点 （encoder の ego 履歴スライス・skip フレーム混入）が症状を素直に説明する。 まず §10 のデータ確認を実施し、その結果で優先順位を決めるのが最短経路。

  • 誤差が横成分にほぼ限定され、発進判断を担う縦成分（goal までの距離）は 2% しかずれない。
  • 破損は |vx| ≥ 2 m/s のサンプル限定で、停車サンプルの goal_pose は当時も正しかった。
  • これは commit メッセージ自身の主張（「横成分を無視するようになり、goal で一定の横オフセットが残る」）と一致する。 すなわち a72126ab が狙って直したのは横オフセットの症状であり、低速発進とは別問題。
  • 副作用として、goal の信頼度が速度域によって非対称（低速では正確・高速では雑音）になり、 共有エンコーダが goal の横チャネルを全体的に減衰させた可能性はある。ただし縦チャネルは入力段で別チャネルなので、 必ずしも同時に減衰しない。

結論 2: 一方「phantom goal（goal 無し → 自車位置が goal）」は変更の前後で全く同じ

変更前はマスクも無かったので、goal_pose = (0,0,0) は heading_to_cos_sin で (0,0,1,0) になったまま素通りしていた。変更後もマスクは（3 列コーパスでは）発火しないので同じ結果である。 つまりこの病理は変更によって生まれたものでも、直ったものでもない。

  • したがって #F（phantom goal）仮説は「変更前から同じ問題が出ていた」という事実によって否定されない。 むしろ変更前から存在していた病理として整合する。
  • 逆に a72126ab は phantom goal を直していない。マスクは「あるように見えて効いていない」状態。

dev では前提が確定している: マスクが死ぬのは goal_pose が 3 列 (x, y, heading) で保存されている場合だが、dev の npz 変換器はまさに 3 列で書き出す （ros_scripts/convert_cpp_bin_to_python_npz.py:194-198）:

# goal_pose (4,) -> (3,)

result["goal_pose"] = cos_sin_to_heading(goal_flat).reshape(3)

C++ 側が「goal 無し」を (0,0,0,0) で表していれば cos_sin_to_heading は arctan2(0,0) = 0 により (0,0,0) を書き出し、学習時に heading_to_cos_sin が (0,0,1,0) へ広げる。経路は完全に追跡できており、マスクは確実に発火しない。 残る未知は「変換器が実際にゼロを出力するか」だけ（§10-2）。

補足: そもそも encoder に「goal 無し」を表現する仕組みが無い

  • GoalPoseEncoder.forward は mask = torch.zeros((B, 1), dtype=torch.bool)、 すなわちgoal トークンを常に有効として扱う（encoder.py:743）。 centric_transform でゼロ化してもトークンは消えず、「全ゼロという特定の埋め込み」になるだけ。
  • 3 列コーパスならマスクは一度も発火していないので、モデルはゼロ化された goal_pose を学習時に一度も見ていない。 仮に将来マスクを直しても、その入力パターンは未学習である点に注意。
  • 推論側は self.route is None で早期 return する（diffusion_planner_node.py:254-255）ので、 実機で goal 無しは発生しない。→ phantom goal は学習データ側だけの問題。

9. 推奨アクション

優先度 1 — 低速問題に直結（まず確認、次に修正）

  1. まず §10-2 で goal_pose のゼロ率を実測。 dev の変換器は 3 列で書き出すことが確定しているので、ゼロが 1 件でもあれば #F は実害あり。 その場合は有効性マスクを位置成分のみの判定に変える: 
    mask = torch.sum(torch.ne(inputs["goal_pose"][..., :2], 0), dim=-1) == 0
    この修正は fix/goal_pose_mask ブランチに quintic / bridge 両方ぶん実装済みで、 tier4-main 向けに PR を出している。dev には未適用なので取り込みが必要。 なお GoalPoseEncoder は goal トークンを常に有効扱いするため、 「goal 無し」を表現したいなら encoder 側の mask も併せて直す必要がある。
  2. ［dev 固有］neighbor future の 4 列対応を取り込む（#M, §7.1）。 §10-7 で列数を確認し、4 列が存在するなら tier4-main の shape[-1] == 4 分岐を quintic / bridge 両方に入れる。
  3. 学習リストに skip_for_training フレームが混入していないか確認。 混入していれば train.py にも scene_skip.filter_scene_list を通す （RLVR / preference_optimization 側は既に通している）。
  4. 低速域の augmentation ゲートを見直す。現在の |vx| ≥ 2.0 は 「摂動後の future 再構成が低速で数値的に壊れる」ことへの回避策と思われるが、副作用として 停車〜発進の全域が augmentation 無しになっている。案:
    • 低速専用の軽い augmentation（横オフセットのみ・future はそのまま／縦方向は摂動しない）を別枠で用意する
    • あるいは bridge 版のように「進行(progress)を保存する」定式化にしてゼロ速度を安全に扱う

優先度 2 — 教師データの破壊を止める

  1. quintic の境界条件を「接線成分・符号付き」に直す (:538-561)。 ego_current_state は既に body frame なので、接線成分は射影不要でそのまま取れる: 
    # θ0: 弦ではなく現在 heading（摂動後）
theta0 = torch.atan2(aug_current_state[:, 3], aug_current_state[:, 2])
# v0, a0: body frame の x 成分 = 接線成分（符号付き）。norm は使わない
v0 = aug_current_state[:, 4]          # vx
a0 = aug_current_state[:, 6]          # ax（向心成分 ay は第2項が表現するので混ぜない）
# 終端側も GT 進行方向へ射影して接線成分・符号を保つ
d2  = (fut[:, P] - 2*fut[:, P-1] + fut[:, P-2])[..., :2] / dt**2
aT  = d2[:, 0] * torch.cos(thetaT) + d2[:, 1] * torch.sin(thetaT)
    §6.1 の表のとおり、これで摂動ゼロ時の誤差が 0.20〜1.10 m → 0.01〜0.07 m に落ちる。 「摂動ゼロなら恒等写像」を回帰テストで固定する（tests/test_data_augmentation.py に追加）。
  2. heading 摂動と速度ベクトルを一緒に回す（§6.3）。 摂動を旧フレームで加えて後から回転するのではなく、新 body frame で vy ≈ 0 を保つように (vx, vy)・(ax, ay) を Δθ だけ先回りして回す。vy ±0.5 m/s の摂動は縮小か削除 （実機 twist.linear.y ≈ 0）。
  3. ay を vx 摂動と整合させる（§6.2）。摂動後に ay ← v_new * ω（+ 小さなノイズ）で再計算する。steering は既に同じ流儀で再計算されているので、それに揃える形。
